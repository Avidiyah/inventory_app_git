# N2 — Add CI: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every push to `main` run the full 520-test suite against a real
Postgres before it can reach production, and make it impossible for that suite
to report success while silently skipping half of itself.

**Architecture:** One GitHub Actions workflow with two parallel jobs (`backend`,
`static`) and a third (`deploy`) that runs only on `main` and only after both
pass. `render.yaml` drops `autoDeploy` so the deploy hook becomes the sole path
to production. Before any of that, a four-line guard in `tests/conftest.py`
converts the existing "skip when the database is unreachable" behavior into a
hard failure when `CI=true`, so a misconfigured service container fails loudly
instead of going green.

**Tech Stack:** GitHub Actions, `postgres:16` service container, Python 3.12
(matches `backend/Dockerfile:1`), pytest 9.0.3, Alembic 1.18.4, Node (for
`node --check`), `pip-audit`.

## Global Constraints

- **Python 3.12.** Must match `backend/Dockerfile:1` (`FROM python:3.12-slim`).
- **All backend commands run from `backend/`.** `alembic.ini`, `requirements*.txt`,
  and the `app` package all resolve relative to it.
- **`DATABASE_URL` must be set for *any* pytest run.** `app/database.py:41-42`
  raises `RuntimeError` at import time when it is missing, and
  `tests/conftest.py:23` imports the engine. This is not optional even for the
  181 pure tests.
- **`libzbar0` must be installed before `pip install`.** `pyzbar==0.1.9` wraps
  native `zbar`; without the system library, `import app.main` fails at import
  time and takes the entire suite with it. This is item **N7**'s named trigger
  ("a runtime or base-image change") coming due.
- **The full suite is 520 passing tests.** 425 test functions across 39 files;
  244 of those functions take the `db` fixture. Any CI run reporting materially
  fewer than 520 passed is a failure, not a pass.
- **Do not add a linter, formatter, or type checker.** Explicitly out of scope
  per the N2 entry in `docs/api-hardening-checklist.md`.
- **`pip-audit` reports but does not block** until its baseline output has been
  triaged.
- **No production code changes.** Only `backend/tests/`, `.github/`, and
  `render.yaml` are touched.

### Task 1: The CI skip-guard

**Files:**

**Interfaces:**

- Produces: `handle_unreachable_database(exc: Exception) -> NoReturn` — always
  raises. `RuntimeError` when `CI` is `"true"`, otherwise calls `pytest.skip`.

- [ ] **Step 1: Write the failing test**

Create `backend/tests/test_db_availability_guard.py`:

```python
"""The guard that stops CI reporting success over a half-skipped suite.

`conftest.py` skips DB-backed tests when Postgres is unreachable so that a
contributor without a local database can still run the 181 pure tests. In CI
that same skip is a liability: 244 of 425 test functions take the `db`
fixture, so a bad DATABASE_URL would produce a green run over 43% of the
suite. In CI the unreachable database must be an error instead.
"""

import pytest

from tests._db_availability import handle_unreachable_database


def test_raises_in_ci(monkeypatch):
    monkeypatch.setenv("CI", "true")

    with pytest.raises(RuntimeError) as excinfo:
        handle_unreachable_database(OSError("connection refused"))

    assert "connection refused" in str(excinfo.value)


def test_skips_outside_ci(monkeypatch):
    monkeypatch.delenv("CI", raising=False)

    with pytest.raises(pytest.skip.Exception):
        handle_unreachable_database(OSError("connection refused"))


def test_ci_set_to_false_still_skips(monkeypatch):
    """`CI=false` is not CI. Matches the SQL_ECHO idiom in app/database.py:48."""
    monkeypatch.setenv("CI", "false")

    with pytest.raises(pytest.skip.Exception):
        handle_unreachable_database(OSError("connection refused"))
```

Run from `backend/`:


- [ ] **Step 3: Write the minimal implementation**

Create `backend/tests/_db_availability.py`:

```python
"""What to do when the test database cannot be reached.

Local: skip, so the 181 pure tests still run without Postgres.
CI: raise, because a skipped DB suite there is a false green.
"""

import os
from typing import NoReturn

import pytest


def _running_in_ci() -> bool:
    # Same idiom as SQL_ECHO in app/database.py:48 -- an explicit "true",
    # not mere presence. GitHub Actions sets CI=true on every runner.
    return os.getenv("CI", "").strip().lower() == "true"


def handle_unreachable_database(exc: Exception) -> NoReturn:
    if _running_in_ci():
        raise RuntimeError(
            f"Database unreachable in CI: {exc}\n"
            "CI must run the full suite against a real Postgres. Skipping "
            "here would report success over the 181 pure tests while the "
            "244 db-fixture tests silently vanished. Check the postgres "
            "service container and DATABASE_URL in .github/workflows/ci.yml."
        ) from exc

    pytest.skip(f"database unreachable: {exc}")
```

### Task 2: The backend job — full suite against real Postgres

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: `CI=true` handling from Task 1.
- Produces: a job named `backend` that Task 5's `deploy` job lists in `needs`.

- [ ] **Step 1: Write the workflow**

Create `.github/workflows/ci.yml`:

```yaml
# Every push to main previously shipped to production having run nothing:
# render.yaml set autoDeploy: true and this directory did not exist. The
# 520-test suite is the largest asset in the repo and never executed on the
# path that mattered.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  backend:
    name: Backend suite
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: inventory
          POSTGRES_PASSWORD: inventory
          POSTGRES_DB: inventory_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      # app/database.py raises at import time without this, so it is required
      # even for the tests that never touch the database.
      DATABASE_URL: postgresql://inventory:inventory@localhost:5432/inventory_test
      # Turns tests/conftest.py's unreachable-database skip into an error.
      CI: "true"

    defaults:
      run:
        working-directory: backend

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"   # matches backend/Dockerfile:1
          cache: pip
          cache-dependency-path: backend/requirements-dev.txt

      # pyzbar wraps native zbar. Without this the import fails and takes the
      # whole suite with it -- see N7 in docs/api-hardening-checklist.md.
      - name: Install native zbar
        run: sudo apt-get update && sudo apt-get install -y libzbar0

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-dev.txt

      - name: Run migrations
        run: alembic upgrade head

      - name: Run test suite
        run: python -m pytest -q
```

### Task 3: The static job — syntax, compile, and migration gates

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: nothing from Task 2 (runs in parallel).
- Produces: a job named `static` that Task 5's `deploy` job lists in `needs`.

- [ ] **Step 1: Add the job**

Append to `.github/workflows/ci.yml`, at the same indentation as `backend:`:

```yaml
  static:
    name: Static checks
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: inventory
          POSTGRES_PASSWORD: inventory
          POSTGRES_DB: inventory_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      DATABASE_URL: postgresql://inventory:inventory@localhost:5432/inventory_test

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - uses: actions/setup-node@v4
        with:
          node-version: "20"

      # The manual check performed by hand after every batch so far.
      # 32 non-vendor files; vendor/ is third-party and not ours to fix.
      - name: JS syntax
        run: |
          find backend/static -name '*.js' -not -path '*/vendor/*' -print0 \
            | xargs -0 -r -n1 node --check

      - name: Install native zbar
        run: sudo apt-get update && sudo apt-get install -y libzbar0

      - name: Install dependencies
        working-directory: backend
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Python compile
        working-directory: backend
        run: python -m compileall -q app

      # A merge that brings in two migrations from different branches leaves
      # two heads; `alembic upgrade head` then fails at deploy time, in the
      # container, after the old version is already down.
      - name: Exactly one Alembic head
        working-directory: backend
        run: |
          count=$(alembic heads | grep -c '(head)')
          echo "alembic heads: $count"
          test "$count" -eq 1

      - name: Migration round-trip
        working-directory: backend
        run: |
          alembic upgrade head
          alembic downgrade -1
          alembic upgrade head
```

### Task 5: Gate the deploy

**Files:**
- Modify: `.github/workflows/ci.yml`
- Modify: `render.yaml:31`

**Interfaces:**
- Consumes: job names `backend` (Task 2) and `static` (Task 3).
- Produces: the only path to production.

**Prerequisite — a dashboard action, not code.** In the Render dashboard, open
the `inventory-app` service → Settings → Deploy Hook, and copy the URL. In
GitHub: repo → Settings → Secrets and variables → Actions → New repository
secret, named `RENDER_DEPLOY_HOOK_URL`. The hook URL is a credential — anyone
holding it can trigger a deploy, so it belongs in a secret and never in the
workflow file.

- [ ] **Step 1: Add the deploy job**

Append to `.github/workflows/ci.yml`, at the same indentation as `backend:`:

```yaml
  deploy:
    name: Deploy to Render
    runs-on: ubuntu-latest
    needs: [backend, static]
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - name: Trigger Render deploy
        run: |
          curl --fail --silent --show-error \
            "${{ secrets.RENDER_DEPLOY_HOOK_URL }}"
```

`needs` is what makes this a gate: a red `backend` or `static` job means
`deploy` never starts. `--fail` ensures a rejected hook fails the job rather
than passing on an HTTP error body.

- [ ] **Step 2: Turn off Render's own auto-deploy**

In `render.yaml`, change `autoDeploy: true` (line 31) to:

```yaml
    # CI is the only path to production: .github/workflows/ci.yml triggers a
    # deploy hook after the suite passes. With autoDeploy on, Render would
    # also deploy directly on push and race straight past that gate.
    autoDeploy: false
```

- [ ] **Step 3: Verify the gate holds before merging**

Push a commit to the PR branch with a deliberately failing test:

```bash
echo 'def test_ci_gate_proof(): assert False' >> backend/tests/test_db_availability_guard.py
git commit -am "TEMPORARY: prove the deploy gate blocks a red build"
git push
```

Expected: `backend` fails, and `deploy` shows as **skipped** — not merely
green. Then remove it:

```bash
git checkout HEAD~1 -- backend/tests/test_db_availability_guard.py
git commit -m "Revert deploy-gate proof"
git push
```

- [ ] **Step 4: Confirm `autoDeploy: false` reached Render**

Merge to `main`, then confirm in the Render dashboard that exactly **one**
deploy was triggered and its source is the deploy hook, not a git push. Two

